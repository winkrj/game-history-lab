# Project Context

## Purpose

Game History Read Model Lab reproduces the cost of a large game-history JOIN query and validates a staged response to that observed problem. The intended learning path is Original JOIN, a Read Model, managed bulk rebuild and restart with Spring Batch, and continuous updates with CDC and Kafka.

The primary audience is a Java/Spring developer learning Kotlin while examining data-read and operational trade-offs. This is a laboratory, not a production-ready service or a survey of every possible architecture.

## Source of truth

`PROJECT_DESIGN.md` is the product and experiment design standard. It defines the domain, representative API, stage boundaries, measurements, and completion criteria. This file records the current implementation state and decisions that should not be rediscovered.

## Current phase

Bootstrap completed on 2026-08-10. The next product task is Stage 1: Original JOIN query. No Stage 1 domain schema, seed data, query, API, or benchmark has been implemented during bootstrap.

Stage 1 must establish:

- correct results from the representative API;
- reproducible data beginning around one million records;
- baseline p95 latency, throughput, SQL execution plan, rows read, and resource usage;
- evidence of the JOIN bottleneck, or evidence supporting a larger data set.

## Current architecture

```text
Spring MVC application
        |
   Spring JDBC
        |
      MySQL
```

There is one deployable Spring Boot application. Docker Compose provides only local MySQL. Tests use a real MySQL container through Testcontainers. Application packages beyond the root package are intentionally deferred until Stage 1 behavior establishes useful boundaries.

## Technology decisions

- Java 21 is the runtime and Gradle toolchain because it is locally available and is an LTS release.
- Spring Boot 4.1.0 and Kotlin 2.3.21 are the stable versions generated by Spring Initializr at bootstrap time.
- Gradle 9.5.1 with the Kotlin DSL is checked in through the Gradle Wrapper, so a system Gradle installation is not required.
- Spring MVC is used for the blocking HTTP path; Spring JDBC is used for explicit SQL and execution-plan-oriented experiments.
- MySQL 8.4 is pinned to its LTS release line in Compose and Testcontainers so local and test database behavior match.
- Local MySQL uses host port 3307 by default because port 3306 is already occupied in the development environment. `MYSQL_PORT` can override the host port; the container port remains 3306.
- Testcontainers verifies actual MySQL connectivity. H2 or another in-memory database is not used.
- Database migration tooling is deferred until Stage 1 introduces the first schema.

## Constraints

- Kotlin code should remain readable to someone coming from Java and Spring. Avoid unnecessary DSLs, extension-heavy design, operator overloading, delegated properties, and advanced functional patterns.
- Do not introduce later-stage technology before the preceding stage demonstrates the problem it addresses.
- Keep representative API semantics comparable across stages.
- Do not claim performance improvements without recorded measurements.
- UI, authentication, authorization, administrative functions, cloud deployment, and microservice decomposition are outside the current design.

## Verification

Run `./scripts/verify.sh`. It validates the Compose model, compiles the application, and runs checks including a Testcontainers-backed MySQL connection test.

Bootstrap evidence from 2026-08-10:

- `./scripts/verify.sh`: passed (`BUILD SUCCESSFUL`; one test, zero failures).
- Testcontainers started MySQL 8.4 and the test executed `SELECT 1` through Spring JDBC.
- `docker compose up -d --wait mysql`: passed with the container reported healthy on the default host port 3307.

For local development:

1. Run `docker compose up -d --wait mysql`.
2. Run `./gradlew bootRun`.
3. Run `docker compose down` when finished. Add `--volumes` only when intentionally deleting local database data.

- Reproducible seed-generation approach and exact initial row distribution near one million records.

Resolve these only as part of Stage 1, before implementing the affected behavior.
